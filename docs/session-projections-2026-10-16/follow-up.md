# 第二次排查：审批生命周期清理（2026-10-16）

## 已确认与仍未证明的部分

11:42 重启且明确关闭 HMR 后，同一 CTF2 会话又产生 7 次真实失败（北京时间 11:50:14–11:50:55），涉及 `ctf_teams_status`、`ops_bash`、`get_goal`、`read`。截至该快照共 1127 条记录、25 次该类工具失败。因此，上一轮关闭 HMR **不足以解决**本机故障。组合配置于 11:50:08 再次写入；主动配置事务仍可重建 Loader，不能据此认定具体哪次事务造成失效。

本轮证实了另一处独立缺陷：实际 Cordis 4.0.4 的单个 generator effect 按逆序串行清理；后一个 disposer 抛错或拒绝后，前面的 disposer 被跳过。实际 Auto review 的一个 effect 同时拥有工具审批回调、Auto 注册和退出收尾；收尾失败会留下旧回调。最小复现可让已退出回调读取失活的 `sessionProjections`；真实 Harness 故障注入则表现为审批关闭后的旧回调持续取消工具。

桌面 ASAR 中的 Cordis、Auto review、permissionPresets、agentPresetRegistry、dsh-scope，与测试依赖中的对应文件逐字节相同。该结果支持本轮复现适用于安装版本；**未捕获原会话首次失活的完整堆栈，也未证明是哪次配置或路由变更触发了清理失败**。

## 修复设计

新增可选入口 `@nanmicoder/dsh-ctf-teams/auto-review-cleanup`。该入口加载宿主原审批实现，仅给其 `auto-review lifecycle` 的清理加一层保护：所有 disposer 都尝试执行，结束后汇总错误。其他 effect 原样委托；不全局修改 Cordis，不拦截工具结果冒充成功，不改变模型审批提示、决策、权限预设或沙箱。

兼容入口校验原 Auto review 的名称与 `apply.toString()` SHA-256：

`59ea8b4eb4b785006e2a3f3dd7d248071f7c53e9c7b91334b220ce4df2e8bb52`

只覆盖审计过的 Harness 0.2.0-rc.2 实现。遇到新实现拒绝加载，需要重新审计；不能默认推广到其他版本。普通 CTF 入口与 preset 不会自动启用它。

`cordis.patch.yml` 的 `name` 是匹配条件，不是替换字段；安装必须禁用原条目并插入新条目。新条目仍调用原审批代码。仅禁用原条目而不加载替代入口会丢失 Auto 能力，不是本方案。操作须在完全退出后执行，避免原实现的运行中卸载把 Auto 会话迁到完全权限。新条目和两个编译文件应保存在稳定目录，不能指向会被 build 清理的工作区 `lib`。

## 验收范围

1. 四项单元回归：原生清理缺陷、同条件释放回调、逆序执行与聚合错误、不支持实现拒绝加载。
2. 原真实宿主对照：Auto 开启，退出时注入投影读取错误；重建后首个工具仍被旧回调取消，对照测试按预期失败。
3. 兼容入口真实宿主：相同注入后旧回调消失；新建会话和持久化会话各三轮，共 36 个成功工具调用，覆盖 CTF、目标、读写和真实 PowerShell。每次启动另测一枚无效审批回执：工具报错，待写文件不存在。共 38 次模型审批请求，两个启动均通过。
4. 在工具执行中进行正式默认模型配置事务，核对 request header 的往返路由；HMR 始终关闭。冷启动用 `agents.resume` 和 preset `mount` 恢复旧会话，没有把新建同名会话冒充恢复。
5. 2026-10-16，用户在原始桌面会话只读调用 `ctf_teams_status` 和 `get_goal`，反馈“两个工具均正常”。确认这两个此前受影响的工具已恢复；该项证据来自用户实机反馈，不扩大为全部工具、写入或 shell 均已在原会话验证，也不证明原始触发条件已经完全确定。维护操作未恢复刷题。

模型使用确定性本地适配器；未消耗真实付费模型调用，未向 CTF2 提交 flag。测试证明已确认的清理失败路径得到修复，不保证所有来源的失活上下文都被覆盖。

**额外发现、尚未修复：** 若在保留 Auto 身份的在线会话存在时，完整重建 `permissionPresets` 服务，新服务构造期会先枚举这些会话，而新 Auto integration 尚未注册，出现 `permission: cannot restore preset "auto" without its active integration`。本轮附加故障链实验验证了此限制，兼容入口也不能消除该构造顺序问题。正常完整退出后再启动，服务先初始化、会话后恢复，已通过上述冷恢复测试。运行中不要变更权限配置或安装、卸载插件；此项需要宿主修复，不通过把用户权限自动改为完全权限来掩盖。

## 自动审批与完全权限

当前 Auto 回调先调用 `permissionPresets.current(session)`，再判断是否跳过模型审批；这个读取本身依赖会话投影。即使用户选了完全权限，残留回调若已经持有失活引用，也可能在分支判断前报错。完全权限因此不能保证解决本问题。本轮不调整用户权限。

## 应用与回退

兼容文件、配置备份、桌面重启及数据保留结果，以 [follow-up-validation.json](./follow-up-validation.json) 为准。回退时先完全退出：恢复本轮备份的 profile patch，保留以前的 HMR 缓解设置；兼容文件可留存，未被配置引用时不运行。不要直接在原始故障会话中反复重试，也不要恢复解题来代替只读工具验证。

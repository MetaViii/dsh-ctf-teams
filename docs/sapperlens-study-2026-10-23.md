# 从 SapperLens 学习什么：CTFTeams 的下一步

日期：2026-10-23。本文是对用户提供文章与公开分析资料的架构对照，**不是已实现功能清单**。当前安装基线为 CTFTeams 0.1.31。

## 来源与判断范围

阅读了用户粘贴的《第三届腾讯云智能攻防挑战赛线上赛第一名：sapper-v2 的架构、角色分工与提示词》，并核对 [SapperLens 的说明](https://github.com/inwpu/SapperLens/blob/eebd7ce31c5d6620f1e760b80de774484568c94b/README.md)、[Commander 提示](https://github.com/inwpu/SapperLens/blob/eebd7ce31c5d6620f1e760b80de774484568c94b/prompts/commander_SKILL.md)、[Worker 模板](https://github.com/inwpu/SapperLens/blob/eebd7ce31c5d6620f1e760b80de774484568c94b/prompts/worker_sh_mission_functions.txt)和 [STATE 示例](https://github.com/inwpu/SapperLens/blob/eebd7ce31c5d6620f1e760b80de774484568c94b/prompts/commander_state_0614.md)。固定参考提交为 `eebd7ce31c5d6620f1e760b80de774484568c94b`。

SapperLens 是对 sapper-v2 的独立分析项目，不是原系统的官方源码。其 README 区分 TSecBench v1 的 run 35447 与正式比赛的 run 33879，并区分直接证据、推断和无法证明的结论。日志中出现某条提示，不等于它在所有运行中都被可靠执行；赛事表现也不能单独证明某项设计的因果收益。本文只提炼可验证的工程设计，不导入原提示文件或题目答案。

## 对 CTFTeams 的具体启发

| 可学的做法 | 当前已有能力 | 还缺什么，如何适配 |
| --- | --- | --- |
| 调度上下文与单题执行分开 | 队长规划 DAG、成员各自执行、任务依赖输出有预算；单步题可用 solo。 | 可选纯编排 profile：队长只看紧凑战况和证据引用，把大输出留在成员文件。保留用户明确授权的队长接管，不能一刀切禁止现有直接解题模式。 |
| 同题共享结构化记忆 | JSON 持久化、findings、候选、任务检查点、0.1.31 假设与实验台账。 | 目前没有实体/依赖关系和结论撤销传播。优先补证据引用与失效关系，而非立即引入图数据库。 |

## 第一优先级：阻止错误前提在队伍中升级为事实

文章 a-03 案例给出的教训是：观察可以正确，解释仍可能错误，而且被多次转述后会越来越像事实。共享记忆的价值取决于它是否保留这条边界。

CTFTeams 已将 finding 标为未复核，区分 raw_output、inference、guess，0.1.31 还保留矛盾实验；这些是基础。下一步应增加：

- 将原始观察、解释和基于解释作出的决策分别引用。例如，某请求返回 500 是观察；“服务设计性损坏”是解释；“跳过登录输入测试”是决策。
- 结论记录 `depends_on`、实际复核依据和 `superseded_by`。前置证据被反驳时，标记依赖结论需要重审，并给受影响的**当前执行者**一条合并通知，保留全部历史。
- 增援前先做低成本反证：列出当前路线依赖的关键假设，选择一个最便宜、最可能改变决策的检验。模型共识或多次转述不提高证据等级。
- 文件哈希只验证字节；队长填写“confirmed”也仍需真实复现记录。自动验证若引入，必须走现有授权执行器，并在模型之外核对结果。

验收应覆盖：反驳前提后相关结论变为待复核，原始输出不被删除；重复反驳不反复发消息；暂停/完成后不派发新的求解轮次。

## 第二优先级：队长交接与紧凑战况

建议做一份有版本的结构化交接快照，而非不断把全队输出灌进主会话。由运行时生成队伍/代际、任务与 attempt、候选与平台裁决、资源占用和最近可信增量；模型只补“当前判断、争议和下一步”。两类内容分开标注，长输出引用文件和哈希。

在重要决策、显式交接或实际上下文压力事件时保存。恢复时先读快照，再核对当前状态和所有权，拒绝旧代际覆盖新计划。不要照抄其他 Harness 的 85%/90% 阈值或“每八轮就换人”，先验证 DSH 可用的准确事件与持久化契约。

验收应覆盖：队长冷恢复后能看到未提交候选与下一步，文件引用丢失时标为未知；较旧快照不覆盖新任务；新会话未经显式接管不能写旧队伍。

## 第三优先级：按收益增援和有界实验

先使用现有队长规划模式实现流程纪律：侦察主线 → 不同假设的第二角度 → 有新证据再增援。每项实验写清预测、方法、预期产物、预算和停止条件。已配置的模型路由可以分层使用，但不默认绑定某家模型，也不自动切到更贵的供应商。

停滞不能只看“有没有新 finding”：模型可以不断重复写报告。需要结合去重后的实验、有效证据变化、目标实际响应、平台回执和预算。达到阈值时建议调整或交接，由现有运行状态处理；不要让 idle、paused、completed 状态被计时器反复唤醒。后台脚本的停止也必须依据本任务保存的进程/资源所有权，不能扫描并杀掉所有 Python、代理或 shell。

验收应覆盖：重复报告不刷新有效进展时间；无新证据时不会无限派新人；资源不足返回明确原因；增援预算按配置执行，现有权限和模型选择不变。

## 选择不照搬的部分

- 不复制永久 board/sleep 循环；本插件已有完成/暂停空转的历史故障，继续用有界事件和消费游标。
- 不硬编码三实例、八 pane、某家模型、固定升级分钟数或上下文阈值。它们属于该运行环境。
- 不用 Key 轮换掩盖认证故障；沿用已授权的路由与有界 fallback，不引入新的额度或计费副作用。
- 不将平台 IP 前缀当成授权范围，不把同家族情报里的凭据或 flag 自动迁移到新题。
- 不因“某系统赛事第一”就复制其所有提示。先测单项收益，再决定是否增加第三层代理或复杂记忆组件。

## 用实验决定是否变强

将 0.1.31 作为基线，用固定模型、并发、时间和预算，对同一批有授权且隔离的题目做对照；保留未参与调优的题目，避免复用答案造成泄漏。优先比较真实平台接受数、首次有效突破耗时、重复实验率、错误前提存活时间、人工救援次数和暂停后额外回合数。

成本至少区分未缓存输入、缓存读取、输出、墙钟和 worker-minutes。总 token 不能直接当作账单成本，事实条数也不能直接当作正确性。每个新机制应能说明：哪类失败变少、如何由外部结果验证、增加了多少开销。

本轮只完成分析与本机 0.1.31 安装，不声称上述规划功能已经落地。下一轮建议先做“证据依赖与低成本反证”，再做队长交接，之后引入预算化增援。
